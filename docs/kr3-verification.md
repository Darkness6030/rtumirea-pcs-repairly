Перед миграцией рабочей базы создан `backups/before-kr3.dump`. Он локальный, в Git не входит.
Рабочий bootstrap-пользователь не использовался для изменяющих приёмочных тестов:
у него сохранён временный пароль из `.env` и требование первичной смены.

Первая Docker-сборка столкнулась с обрывом загрузки Hibernate из Maven Central.
После повторной стандартной сборки проблема не воспроизвелась. Для воспроизведения
итогового запуска специальный локальный образ Maven-кэша не требуется.

DOM-тесты исполняют настоящий `app.js` с тестовым DOM и ответами API: проверяют шесть
страниц администратора, интерфейс VIEWER, безопасное отображение введённого текста,
редактирование с version/clientId, повторную фильтрацию, ошибку сохранения и этапы CSV.
Они не проверяют CSS-layout. В Chrome проверены открытие страницы входа и авторизация;
полный ручной проход по экранным сценариям не завершён из-за переключения/закрытия
тестовой вкладки во время проверки. Для него используйте сценарий в `kr3-defense.md`.

## Воспроизведение

Из корня репозитория, JDK 21:

```bash
./mvnw -B -ntp test
./mvnw -B -ntp -f backend/pom.xml verify
node --check backend/src/main/resources/static/app.js
npm --prefix backend ci --ignore-scripts
npm --prefix backend test
```

Node.js 22+ нужен только для DOM-тестов (jsdom). Для запуска готового веб-интерфейса
не нужен ни Node.js, ни npm. CI повторяет Maven и DOM-проверки.

## Интеграционные HTTP-проверки на PostgreSQL

Нужны Python 3.9+, JDK 21 в PATH, настроенный `.env`, запущенный Compose postgres и
собранный `backend/target/repairly-backend-1.0.0.jar`.

```bash
./backend/init-env.sh
docker compose up -d --wait postgres
./mvnw -B -ntp -f backend/pom.xml package

# Создать отдельную базу со схемой КР1 + demo seed, мигрировать и проверить:
python3 backend/scripts/verify_postgres.py

# Проверить создание всей схемы на пустой базе:
python3 backend/scripts/verify_postgres.py --fresh

# Проверить миграцию собственной резервной копии КР1:
python3 backend/scripts/verify_postgres.py --backup backups/before-kr3.dump
```

На Windows используются `mvnw.cmd`, `backend/init-env.ps1` и команда `python` вместо
`python3`, если так установлен Python.

Скрипт создаёт `repairly_verify_<случайный суффикс>`, поднимает локальный JAR на свободном
порту с отдельным JWT-секретом и bootstrap-пользователем, затем выполняет `verify_api.py`.
В `finally` сервер останавливается и удаляется только созданная тестовая база.
Настоящая база `DB_NAME` не очищается и её администратор не изменяется. Режим `--backup`
ожидает исходную базу КР1 без пользователей backend и минимум три записи в каждом
справочнике. Это не тест произвольного дампа уже работающей КР3.

Лог тестового сервера: `backend/target/verification.log`. Не запускайте два экземпляра
runner одновременно: файл журнала общий. При принудительном завершении процесса вне
Python (например, kill -9 или выключении компьютера) finally не гарантирован; имя
незавершённой тестовой базы печатается при старте.

Прямой запуск `verify_api.py` принимает `VERIFY_URL`, `VERIFY_EMAIL`, `VERIFY_PASSWORD`
и **изменяет данные/пароль указанного пользователя**. Поэтому предпочтителен runner,
который создаёт отдельное окружение автоматически. Не направляйте тест на рабочий URL.

## Что покрывают 106 HTTP-проверок

- Health, 401 без токена, защита Swagger, обязательная замена временного пароля.
- Отзыв старого access после смены/сброса пароля; refresh-ротация, повторное использование,
  отзыв refresh при logout, блокировка после пяти ошибок входа.
- Чтение исходных данных, CRUD клиента/мастера/заявки, числовая валидация, связи,
  запрещённый переход статуса, конфликт версий 409.
- Комбинация текстового поиска и всех фильтров, точное совпадение кода мастера,
  сортировки, разные страницы, верхняя граница размера страницы и белый список сортировок.
- Создание, изменение и удаление заметки, версия заметки, запрет изменения чужой заметки.
- Частичный успех массового добавления тега, снятие тега, смена статуса, архив/восстановление.
- Архивный фильтр, восстановление, физическое удаление ADMIN с подтверждением.
- Экспорт отфильтрованных строк, UTF-8 BOM, preview/apply, повторный номер, upsert,
  некорректная строка, отсутствующий файл (400) и аналитическая сводка.
- VIEWER/EDITOR: запрет административных функций; отключённые учётные записи.
- Автор входа в аудите и `X-Correlation-ID` в ответах API.

HTTP-проверки проходят против настоящей PostgreSQL. H2 smoke-тест сам по себе не
проверяет PostgreSQL-миграции, триггеры, индексы и особенности SQL, поэтому эти виды
проверок разделены.
