# КР №2: сценарий защиты Repairly

## Демонстрация (7–10 минут)

1. Показать ветки `kr1` и `kr2`. В `kr1` сохранено консольное приложение, в `kr2` —
   развитие той же предметной области. Показать три прежние таблицы PostgreSQL.
2. Выполнить `docker compose up -d --wait`, затем `docker compose ps`.
   Объяснить volume, опубликованный порт, healthcheck и сохранение данных при `down`.
   Для системы преподавателя показать отдельный backend и `/actuator/health`
   по инструкции `reference-example.md`.
3. Запустить `./mvnw javafx:run`. Показать список заявок и сведения выбранной строки.
4. В «Клиенты» создать запись с вымышленными контактами. Попытаться сохранить пустое
   имя и повторяющийся телефон; исправить ошибки. Создать мастера аналогично.
5. Создать заявку, выбрав клиента из списка. Показать ошибку отрицательной стоимости.
   Сохранить корректную заявку и найти её по клиенту / модели техники.
6. Открыть заявку, назначить мастера и перейти в «Диагностика» одним сохранением.
   Затем «В ремонте» → «Завершена». Объяснить недоступность редактирования закрытой заявки.
7. Совместить фильтры по статусу и мастеру; выбрать период. Задать обратный диапазон
   дат и показать ошибку. Сбросить фильтры. Отсортировать стоимость и дату, в том числе
   Shift + щелчок по второму столбцу.
8. Из справочника перейти к связанным заявкам. Попытаться удалить используемого клиента:
   после подтверждения БД отклонит удаление, история останется.
9. Открыть статистику и объяснить все восемь показателей. Отменённые заявки не входят
   в открытые и в стоимость завершённых. Среднее на пустом наборе равно нулю.
10. Отфильтровать несколько заявок, выбрать «Экспорт CSV», сохранить через FileChooser
    и открыть файл. В нём только видимые строки, в текущем порядке сортировки, с именами
    людей вместо внешних ключей.
11. Удалить созданную для показа заявку: сначала отменить подтверждение, затем подтвердить.
    Удалить её клиента и мастера, если других связанных заявок нет. Нажать «Обновить».
12. При необходимости показать отчёт тестов `target/surefire-reports`.

## Что объяснять по коду

| Вопрос | Ответ и точка входа |
| --- | --- |
| Stage, Scene, Node | Stage — окно ОС, Scene — содержимое окна, Node — элемент дерева интерфейса. `RepairlyApplication.start` создаёт Stage/Scene из загруженного FXML. |
| Зачем FXML | Разметка и композиция интерфейса отделены от поведения. `fx:controller` задаёт контроллер, `fx:id` связывает элемент с `@FXML`-полем, `onAction="#save"` вызывает обработчик. |
| Как разделяются экраны | `main.fxml` включает другие FXML через `fx:include`. `MainController` переключает видимость и managed-состояние страниц. |
| Как обновляется TableView | У Workspace есть ObservableList. После успешной фоновой загрузки `setAll` выполняется на FX-потоке. TableView наблюдает SortedList поверх FilteredList и исходного списка. |
| Почему не JavaFX-свойства во всех моделях | Модели — неизменяемые Java records без привязки к UI. Изменение данных публикуется заменой элемента / списка. DAO и сервисы можно повторно использовать в КР №3. |
| Поиск и фильтры | `RequestFilter` — предикат: поиск по смысловым полям, статус, мастер, включительный период. Условия объединяются AND, поиск не зависит от регистра. |
| Сортировка | `SortedList.comparatorProperty` связан с `TableView.comparatorProperty`. Дата — LocalDateTime, стоимость — BigDecimal, поэтому сортировка не строковая. |
| Бизнес-логика | Сервисы проверяют строки, стоимость, связи, уникальность телефона, переходы статусов и закрытые заявки. Controller собирает введённые значения и вызывает сервис. |
| JDBC и DAO | Repository открывает Connection, использует PreparedStatement с параметрами, закрывает Connection/Statement/ResultSet через try-with-resources. SQL находится только в repository. |
| Атомарность формы | После полной проверки вся заявка сохраняется одним INSERT / UPDATE, а не последовательностью отдельных сохранений её полей. PostgreSQL выполняет statement атомарно. |
| Одновременное редактирование | При открытии формы запоминается version. UPDATE содержит `WHERE id = ? AND version = ?` и увеличивает version. Устаревшая форма получает ошибку. |
| Почему интерфейс не зависает | FxTasks выполняет JDBC и CSV вне FX-потока. `Task.setOnSucceeded` / `setOnFailed` возвращают управление UI. Во время сохранения повторная отправка и закрытие формы блокируются. |
| Исключения | DAO переводит SQLState в прикладное исключение, GUI показывает понятное сообщение. Причина сохраняется в логах; пользовательский ввод остаётся в форме. |
| Статистика | StatisticsService агрегирует снимок заявок: количества, суммы BigDecimal, среднее с HALF_UP. Контроллер выводит показатели и диаграмму по статусам. |
| CSV | Контроллер делает `List.copyOf(table.getItems())`, FileChooser выбирает путь. CsvExportService записывает UTF-8, экранирует кавычки и защищает текстовые поля от интерпретации как формул. |
| Docker и JDBC | PostgreSQL слушает 5432 в контейнере, JDBC использует опубликованный порт компьютера. JavaFX выполняется на компьютере. Backend нужен учебному Student Hub, а собственная КР №2 работает напрямую с PostgreSQL. |

## Распределение подготовки в команде

Состав команды КР №1 сохраняется. Можно распределить подготовку на четыре направления:
FXML/CSS и навигация; формы/валидация; JDBC/бизнес-правила/Docker; статистика/экспорт/тесты.
Каждый участник должен самостоятельно пройти весь сценарий и объяснить любую строку
в таблице выше. Имена и вклад участников следует указывать по фактической работе команды.
