# Repairly — сервис ремонта бытовой техники

Учебное консольное приложение для учёта **заявок на ремонт бытовой техники**.
Архитектура и набор разделов созданы по аналогии с
[rtumirea-pcs-meetly](https://github.com/kosheeta/rtumirea-pcs-meetly): Java, JDBC,
PostgreSQL, Gradle, русское консольное меню, поиск, фильтрация, сортировка,
статистика и экспорт в Excel. Предметная модель и прикладной код написаны для сервиса ремонта.

## Возможности

- Создание, просмотр, редактирование и удаление клиентов и мастеров.
- Регистрация заявки: клиент, вид техники, бренд, модель, описание неисправности.
- Назначение и смена мастера, изменение стоимости и сведений о технике.
- Переходы между статусами ремонта, отмена и удаление заявки с подтверждением.
- Поиск по номеру, клиенту, мастеру, технике и тексту неисправности.
- Фильтрация по статусу; сортировка по дате, стоимости и статусу.
- Статистика по статусам, общая и средняя стоимость завершённых ремонтов.
- Excel-отчёт с листами «Клиенты», «Мастера» и «Заявки».

## Требования

- JDK **21 или новее** (код компилируется для Java 21).
- Docker с Docker Compose для PostgreSQL 17.
- Интернет при первой сборке для загрузки Gradle и зависимостей.

Gradle отдельно устанавливать не нужно: Wrapper включён в репозиторий.
В отличие от исходного проекта JDK 25/26 не требуется.

## Быстрый запуск

Все команды выполняются из каталога проекта.

```bash
cp .env.example .env
docker compose up -d --wait
```

Схема создаётся автоматически при первом запуске PostgreSQL с новым volume.
Используется отдельная БД `repairly`, порт **55432**, доступный только на localhost.
В `.env.example` указан учебный локальный пароль; `.env` исключён из Git.
Если порт занят, поменяйте **оба** значения `DB_PORT` и порт в `DB_URL`.

По желанию загрузите демонстрационные данные:

```bash
docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < src/main/resources/db/migration/seed.sql
```

Скрипт добавляет три клиента, трёх мастеров и шесть заявок — по одной на каждый
статус. Он не удаляет данные и при повторном выполнении не дублирует неизменённые
демонстрационные записи. Все имена, адреса и телефоны вымышлены.

macOS / Linux:

```bash
./gradlew -q --console=plain run
```

Windows PowerShell (настройку `.env` можно выполнить командой `Copy-Item .env.example .env`):

```powershell
.\gradlew.bat -q --console=plain run
```

Выберите `0`, чтобы вернуться из раздела или завершить программу. Закрытие
стандартного ввода также корректно завершает приложение.

### Запуск на локальной Java (macOS)

Приложение запускается обычным процессом Java на компьютере. Docker нужен для PostgreSQL.
На этой машине доступен JDK 21 из PyCharm; отдельный системный JDK не зарегистрирован.
Полная последовательность запуска из нового терминала:

```bash
cd ~/PycharmProjects/rtumirea-pcs-repairly
export JAVA_HOME="/Applications/PyCharm.app/Contents/jbr/Contents/Home"
export PATH="$JAVA_HOME/bin:$PATH"

java -version
javac -version

# Создать настройки только при их отсутствии.
[ -f .env ] || cp .env.example .env

docker compose up -d --wait
./gradlew -q --console=plain run
```

Docker Desktop должен быть запущен. При первом запуске Gradle скачает зависимости.
Для выхода выберите `0`. Переменные `JAVA_HOME` и `PATH` действуют в текущем терминале.

Если установлен отдельный JDK 21, вместо пути к PyCharm можно выбрать его:

```bash
export JAVA_HOME="$(/usr/libexec/java_home -v 21)"
export PATH="$JAVA_HOME/bin:$PATH"
```

После однократной сборки приложение можно запускать напрямую, без Gradle:

```bash
./gradlew installDist
./build/install/rtumirea-pcs-repairly/bin/rtumirea-pcs-repairly
```

Эта команда также использует локальную Java из `JAVA_HOME`. Выполняйте её из корня
проекта, чтобы приложение прочитало `.env`. После изменения кода повторите `installDist`.

Остановить БД без удаления данных:

```bash
docker compose stop
```

При следующем запуске достаточно `docker compose up -d --wait` и команды `run`.
Команда `docker compose down` сохраняет volume; опция `-v` удаляет базу и её данные.

## Пример работы

1. В «Клиенты» добавьте клиента и запомните ID (или используйте демоданные).
2. В «Мастера» добавьте мастера и запомните ID.
3. В «Заявки на ремонт» создайте заявку с ID клиента.
4. Назначьте мастера, переведите заявку в «Диагностика».
5. Отредактируйте стоимость и описание; выберите «В ремонте», затем «Завершена».
6. Проверьте статистику и выполните экспорт. Пустой путь сохраняет файл в `exports/`.

Существующий Excel-файл не перезаписывается: для нового отчёта укажите другой путь.
Стоимость хранится в `BigDecimal` / `NUMERIC(12, 2)`, ввод допускает точку или запятую.
Нулевая стоимость разрешена, например для гарантийного ремонта. Учёт оплаты не ведётся:
статистика показывает стоимость завершённых работ, а не фактически полученные платежи.

## Статусы и правила

| Статус | Допустимые следующие статусы |
| --- | --- |
| Новая | Диагностика, Отменена |
| Диагностика | Ожидание запчастей, В ремонте, Отменена |
| Ожидание запчастей | В ремонте, Отменена |
| В ремонте | Ожидание запчастей, Завершена, Отменена |
| Завершена | Нет |
| Отменена | Нет |

Диагностика и последующие этапы требуют назначенного мастера. Время создания и
завершения устанавливается автоматически. Закрытые заявки не редактируются.
Удаление заявки доступно как отдельное действие с подтверждением; это удаляет её
из истории и статистики. Клиента или мастера со связанными заявками удалить нельзя.
Телефон уникален внутри каждого справочника; пробелы, скобки и дефисы убираются.
Поле `version` защищает изменения заявки от одновременной перезаписи из двух процессов.

## Структура

```text
src/main/java/ru/rtumirea/repairly/
  Main.java             — сборка зависимостей и запуск
  model/                — Client, Technician, RepairRequest, RepairStatus
  repository/           — JDBC-запросы, параметризованные значения
  service/              — правила, проверки, статистика, Excel
  ui/                   — консольное меню и ввод
  util/                 — подключение к БД из окружения / .env
  exception/            — ошибки предметной области
src/main/resources/db/migration/
  initial.sql           — таблицы, связи, ограничения, индексы
  seed.sql              — необязательные демонстрационные данные
src/test/java/          — интеграционные и функциональные проверки
docs/                  — ER-диаграмма и описание модели
```

## Проверки

```bash
./gradlew test
./gradlew build
```

По умолчанию тесты создают изолированные H2-базы в режиме совместимости с PostgreSQL.
Проверяются CRUD, полный цикл ремонта, неверные переходы, валидация, ограничения БД,
связанные удаления, конкурентные обновления, поиск, статистика, содержимое XLSX и ввод.

Тот же набор можно выполнить на реальном PostgreSQL. Тесты создают временную схему
на каждый сценарий и удаляют только эту схему после проверки; таблицы `public` не затрагиваются.
Пользователь БД должен иметь право `CREATE` на базу.

```bash
TEST_DB_URL=jdbc:postgresql://localhost:55432/repairly \
TEST_DB_USER=repairly TEST_DB_PASSWORD=repairly_local_dev \
./gradlew test --rerun-tasks
```

При изменении `.env` подставьте актуальные реквизиты. HTML-отчёт: `build/reports/tests/test/index.html`.

## Подключение GitHub позже

Локальный Git-репозиторий не требует интеграции с GitHub. После создания пустого
репозитория в своём аккаунте выполните:

```bash
git remote add origin git@github.com:YOUR_LOGIN/rtumirea-pcs-repairly.git
git push -u origin main
```

Не публикуйте `.env`, выгрузки с персональными данными и каталоги сборки — они уже
включены в `.gitignore`.
