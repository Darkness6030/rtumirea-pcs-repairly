# Repairly — сервис ремонта бытовой техники

**Контрольная работа №2:** настольное приложение на JavaFX 21 с прямым JDBC-подключением
к PostgreSQL из КР №1. Предметная область, таблицы, данные и правила ремонта сохранены.
Основная сущность — заявка на ремонт; связанные справочники — клиенты и мастера.

- `kr1` — снимок консольного приложения, включая изменения на момент начала КР №2.
- `kr2` — JavaFX, FXML, CSS и Maven; текущая разработка.

## Запуск

Нужны **JDK 21** и запущенный **Docker с Compose**. JavaFX работает на компьютере,
PostgreSQL — в Docker. Для Repairly сервер REST API не требуется.
Maven 3.9.11 загружается включённым Maven Wrapper; при наличии Maven 3.9+ можно
заменять `./mvnw` на `mvn`. Первая сборка требует интернета.

macOS / Linux, из корня проекта:

```bash
./run.sh
```

Windows PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File .\run.ps1
```

Скрипты создают `.env` из примера **только при его отсутствии**, запускают PostgreSQL
с ожиданием healthcheck, затем выполняют `javafx:run`. Существующая база не очищается.

Та же последовательность вручную:

```bash
cp .env.example .env              # только если .env ещё нет!
docker compose up -d --wait
./mvnw javafx:run
```

В Windows используются `Copy-Item .env.example .env` и `.\mvnw.cmd javafx:run`.
В IntelliJ IDEA откройте **pom.xml**, выберите JDK 21 и запустите Maven → Plugins →
javafx → javafx:run. Рабочий каталог — корень проекта, где находится `.env`.

### Настройки базы

Несекретные значения по умолчанию находятся в `src/main/resources/database.properties`.
Переменные окружения имеют приоритет над `.env`, а `.env` — над значениями по умолчанию.
Пароль читается только из `DB_PASSWORD` в окружении / `.env`.

| Настройка | Назначение |
| --- | --- |
| `DB_URL` | JDBC URL, по умолчанию `jdbc:postgresql://localhost:55432/repairly` |
| `DB_PORT` | Публикуемый Docker-порт, по умолчанию `55432` |
| `DB_NAME` | База КР №1: `repairly` |
| `DB_USER` | Пользователь PostgreSQL |
| `DB_PASSWORD` | Пароль PostgreSQL; локальный учебный пример есть в `.env.example` |

Если порт занят, поменяйте **DB_PORT и порт в DB_URL одновременно**. На машине,
где проверялась КР №2, используется `55434`: `55432` занят локальным PostgreSQL.
Это локальное изменение `.env`, а не изменение схемы или Docker volume.

При запуске из иного рабочего каталога можно передать JVM-свойство
`-Drepairly.config=/каталог/с/.env` (например, в VM options конфигурации IDE).
Смена пароля в `.env` не меняет пароль пользователя в уже созданной базе.

### Демонстрационные данные

При новом Docker volume автоматически выполняется `initial.sql`. Существующий volume
`repairly_postgres_data` сохраняется и используется без миграции: схема КР №1 не менялась.

Загрузить тестовый набор из 3 клиентов, 3 мастеров и 6 заявок:

```bash
docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < src/main/resources/db/migration/seed.sql
```

Для Windows PowerShell:

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
Get-Content -Raw -Encoding UTF8 src/main/resources/db/migration/seed.sql | docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Скрипт не удаляет записи и не дублирует неизменённые демоданные при повторном запуске.
Все контакты вымышлены. После загрузки нажмите **Обновить** в приложении.

Остановка без потери данных:

```bash
docker compose down
```

Не добавляйте `-v`: эта опция удаляет volume с базой данных.

## Возможности интерфейса

**Заявки.** TableView с номером обращения, техникой, клиентом, статусом, датой,
стоимостью и мастером. Выбор строки открывает подробности: неисправность, телефон
и адрес клиента, контакты и специализация мастера, даты приёма и завершения.
Техническая версия и внешние ключи в таблице не показываются.

- Создание заявки, редактирование открытой заявки, удаление с подтверждением.
- Клиент и мастер выбираются из ComboBox; вводить ID не требуется.
- Поиск по номеру, виду техники, бренду, модели, неисправности, клиенту, его телефону и мастеру.
- Совместные фильтры: **статус**, **мастер / не назначен**, **период приёма включительно**.
- Сортировка нажатием заголовков, в том числе по дате и числовой стоимости;
  Shift + щелчок добавляет второй столбец сортировки.
- CSV текущего отфильтрованного списка **в порядке таблицы** через FileChooser.
  UTF-8 с BOM, разделитель `;`, кавычки и переводы строк экранируются,
  потенциальные формулы открываются как текст. Замена файла требует подтверждения.
- Кнопка **Обновить** перечитывает БД; после CRUD данные перечитываются автоматически.

**Клиенты и мастера.** Полный CRUD, поиск, сортировка и переход к связанным заявкам.
Для новой базы сначала добавьте клиента, затем зарегистрируйте заявку.

**Статистика.** Восемь показателей для всех загруженных заявок: всего, открытые,
завершённые, доля завершённых, число клиентов, число мастеров, общая и средняя
стоимость завершённых ремонтов. Диаграмма показывает количество по шести статусам.
Фильтры таблицы не влияют на статистику — это явно указано на экране.
Стоимость работ не означает фактически полученные платежи.

## Бизнес-правила и валидация

| Текущий статус | Допустимые следующие статусы |
| --- | --- |
| Новая | Диагностика, Отменена |
| Диагностика | Ожидание запчастей, В ремонте, Отменена |
| Ожидание запчастей | В ремонте, Отменена |
| В ремонте | Ожидание запчастей, Завершена, Отменена |
| Завершена / Отменена | Нет |

- Диагностика и ремонт требуют назначенного мастера; закрытая заявка не редактируется.
- Клиент закрепляется при создании. Даты устанавливаются автоматически; завершение
  не может предшествовать приёму. В фильтре проверяется корректность диапазона дат.
- Обязательные строки, длина полей, телефон (10–15 цифр), существование связей
  и уникальность телефона проверяются сервисами; ограничения PostgreSQL страхуют
  конкурентные операции. Пробелы, скобки и дефисы в телефоне нормализуются.
- Стоимость: от 0 до 9 999 999 999,99, максимум 2 знака после запятой; допустима точка.
- Форма сохраняется одним INSERT / UPDATE после проверки всех полей. При ошибке
  введённые значения остаются в форме; причина отображается рядом с кнопками.
- `version` защищает открытую форму от перезаписи изменений другого клиента.
- Клиента / мастера со связанными заявками удалить нельзя (FK `RESTRICT`).
- JDBC и запись CSV выполняются фоновыми Task. Интерфейс показывает ход операции
  и понятные ошибки; SQL и stack trace пользователю не выводятся.

## Архитектура

```text
pom.xml, mvnw, mvnw.cmd       Maven + Wrapper 3.9.11
run.sh, run.ps1               Docker PostgreSQL → локальный JavaFX
src/main/java/ru/rtumirea/repairly/
  Main.java                  точка входа
  fx/                        Application, общие окна, фоновые задачи, ObservableList
  fx/controller/             контроллеры заявок, справочников, форм и статистики
  model/                     записи предметной области и снимок связанных данных
  service/                   бизнес-правила, фильтры, статистика, экспорт
  repository/                DAO: JDBC, PreparedStatement, закрытие ресурсов
  util/                      конфигурация подключения
  exception/                 прикладные исключения
  ui/                        сохранённый код консоли КР №1 для регрессионных тестов
src/main/resources/
  database.properties        настройки без пароля
  db/migration/              прежняя схема и демонстрационные данные КР №1
  ru/rtumirea/repairly/fx/    шесть FXML-файлов и app.css
src/test/java/               тесты бизнес-правил, DAO, экспорта и JavaFX
```

`MainController` переключает разделы. У заявок, справочников, статистики и форм
отдельные контроллеры. Клиенты и мастера используют общий контроллер справочника.
`Workspace` координирует обновление ObservableList, `FxTasks` переносит I/O в рабочие
потоки. Controller не содержит SQL. Сервисы не зависят от JavaFX.

Сохранённые консольный UI и полный XLSX-экспорт КР №1 не являются точкой входа КР №2.
Gradle остаётся в ветке `kr1`; в `kr2` используется Maven.

## Проверки

```bash
./mvnw clean verify                 # 60 проверок сервисов / JDBC / CSV / прежнего XLSX
./mvnw -Pgui-tests test             # ещё 4 сценария с настоящими JavaFX-окнами
```

Обычные тесты используют временные H2-базы в PostgreSQL-режиме. Профиль `gui-tests`
требует графической сессии; на Linux можно запустить через `xvfb-run -a`.

Тот же набор на настоящем PostgreSQL (подставьте свои параметры `.env`):

```bash
TEST_DB_URL=jdbc:postgresql://localhost:55434/repairly \
TEST_DB_USER=repairly TEST_DB_PASSWORD=repairly_local_dev \
./mvnw -Pgui-tests test
```

Каждый сценарий создаёт и удаляет только собственную временную схему. Данные
`public` не меняются. Результаты — `target/surefire-reports`.
`package` создаёт обычный JAR; для запуска с JavaFX-зависимостями используйте
`javafx:run`, а не `java -jar` без classpath / module path.
